Instructor lesson plan

Teaching simple_robot in one hour

A guided session for students who can already code but have never touched ROS 2 or Gazebo — using the differential-drive robot, lidar, and reactive obstacle-avoidance node you already have running.

⏱ 60 minutes 🎓 Some programming, new to ROS 💻 Hands-on, per-student or paired 📦 Package: simple_robot

What they should walk out with

Not a full ROS 2 course — one hour buys three solid mental models. Everything below is built to serve these.

  1. 1Nodes talk over topics, not function calls. A node publishes a message; anything subscribed gets it — they never call each other directly.
  2. 2Sense → think → act is a loop, not a script. The lidar scan comes in, a decision gets made, a velocity goes out — every single scan, forever.
  3. 3The same robot can be driven two ways. A human typing keys and eleven lines of Python are both just “something publishing to /cmd_vel.”

Before the room fills up

Three real failure modes I hit while building this — they will eat your one hour if you meet them live instead of in advance.

  • Confirm the Gazebo window actually renders on every machine. The lidar sensor needs real GPU rendering. On a machine without one, /lidar silently publishes nothing — the robot looks “broken” with no error message. Test each laptop the day before, or plan to pair students onto machines you've already checked.
  • Kill leftover simulator processes between runs. Two Gazebo instances answering to the same world/robot name cross-talk over the bridge in ways that are confusing to debug live. Have students run pkill -f "ign gazebo" before every relaunch, as a reflex, not just when something looks wrong.
  • Pre-build the workspace. Run colcon build --packages-select simple_robot yourself beforehand and confirm ros2 launch simple_robot obstacle_avoidance.launch.py opens Gazebo with the robot visibly driving and turning. Don't debug a build error in front of the class.

Session script

1. The sense–think–act loop

0–8 min · no laptops open

Land the one idea everything else hangs off, before anyone touches a keyboard.

Draw this on the board exactly as three boxes, nothing fancier:

Lidar sensorgz gpu_lidar
→/lidar→
obstacle_avoidancea ROS 2 node
→/cmd_vel→
Wheel motorsdiff_drive plugin

Say plainly: the box in the middle never touches a motor and never touches a sensor. It only ever does one thing, over and over: read a number, decide, publish a number. That's the entire mental model for a ROS 2 node.

Say

“A topic isn't a wire between two specific programs. It's a named mailbox. obstacle_avoidance doesn't know or care what's reading /cmd_vel — it could be a real motor, a simulated one, or nothing at all.”

2. Live demo: watch it think

8–20 min · instructor's screen only

Make the diagram from block 1 undeniably real before students touch anything.

On your machine, projected:

# terminal 1
cd ~/ros2_ws && source install/setup.bash
ros2 launch simple_robot obstacle_avoidance.launch.py

While Gazebo opens, narrate the three processes launch.py just started: the simulator, the bridge, and the avoidance node — three separate programs that have never seen each other's source code.

# terminal 2, once the robot is driving
ros2 topic list
ros2 topic echo /cmd_vel

Point at the numbers scrolling by. This is the “mailbox,” live. When the robot turns toward an obstacle, pause and read the node's own log line off terminal 1 — it prints exactly what it saw and what it decided.

Watch for

If ros2 topic hz /lidar shows nothing, the GPU isn't rendering the sensor on that machine — switch to a machine you tested beforehand rather than debugging drivers live.

3. Hands-on: drive it yourself

20–35 min · every student

Feel the keypress→topic→motion chain with their own hands before reading anyone's code.

Each student (or pair), two terminals:

# terminal 1 — simulation only, no autopilot
ros2 launch simple_robot manual_control.launch.py
# terminal 2 — keyboard teleop
ros2 run teleop_twist_keyboard teleop_twist_keyboard
KeyDoes
idrive forward
,drive backward
j / lturn left / right in place
kstop

Have them run ros2 topic echo /cmd_vel in a third terminal (or split their screen) while driving, so they see their own keypresses arrive as numbers — the same mailbox as block 2, just with a human as the publisher instead of a node.

Ask the room

“What's actually different, from the wheel motor's point of view, between me driving and the algorithm driving?” — steer toward: nothing. Both just publish a Twist.

4. Hands-on: read the robot's brain

35–50 min · every student

Connect the code they can read to the behavior they already watched twice.

# kill teleop and manual_control first, then:
ros2 launch simple_robot obstacle_avoidance.launch.py

While it runs, open obstacle_avoidance.py on the projector and walk it in this order — each maps directly to a box from block 1's diagram:

  1. create_subscription(LaserScan, '/lidar', ...) — this is the arrow into the box.
  2. Inside lidar_callback: it only looks at a narrow cone straight ahead (±34°) and takes the closest reading in it — the “sense” step.
  3. The if/else on that distance — the “think” step. Ask: why compare against a fixed number like 1.0? What would too small or too large break?
  4. self.publisher.publish(cmd) — the arrow out of the box, straight back to block 1's diagram.
Discussion hook

This version also picks which side to turn based on which has more room, instead of always turning the same way. Ask students to predict, before you show them: what goes wrong with a robot that always turns left, no matter what it sees?

5. Mini-challenge & wrap

50–60 min

Send them out with something to try, not just something they watched.

Pose one live, no laptops needed to discuss it: the robot only checks a 34° cone directly ahead. Where on this map could you put an obstacle that it would never see coming? Let a couple of students reason it out loud — the answer (anything approaching from the side) sets up next session's topic (wider sensing, or multiple sectors) for free.

Close by naming the three things from “what they should walk out with” explicitly, in one sentence each. Students remember the recap better than the middle.

If you have a second session

Take-home or follow-up exercises, roughly in order of difficulty.

  • Change SAFE_DISTANCE and TURN_SPEED in obstacle_avoidance.py and predict the effect before running it.
  • Add a third box to obstacle_world.sdf and see whether the robot still clears it cleanly.
  • Widen or narrow the forward detection cone (FRONT_ANGLE) and find where it starts missing obstacles or overreacting to open doorways.
  • Sketch (pseudocode is fine) how you'd make the robot check its sides while driving forward, not just its front.

Command reference

Print this page or keep it open on a second monitor during the session.

# one-time build, before class starts
cd ~/ros2_ws
colcon build --packages-select simple_robot
source install/setup.bash

# automatic (obstacle avoidance)
ros2 launch simple_robot obstacle_avoidance.launch.py

# manual (two terminals)
ros2 launch simple_robot manual_control.launch.py
ros2 run teleop_twist_keyboard teleop_twist_keyboard

# inspect what's flowing
ros2 topic list
ros2 topic echo /cmd_vel
ros2 topic hz /lidar

# between any two runs
pkill -f "ign gazebo"
